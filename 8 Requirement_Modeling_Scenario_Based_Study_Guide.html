Requirement Modeling,
sketched through SafeHome

After two break-ins on their street in one month, the Rao family decides they need a smart home security system — SafeHome. But before a single sensor is coded, every requirement has to be turned into a picture the whole team can agree on. That's Requirement Modeling.

1 The Core Idea

Why draw it, when you could just write it?

The Rao family can describe SafeHome in a sentence. A development team can't build from a sentence — they need to see it.

The Story

Mr. Rao tells the developer:

"I want a system that arms itself, watches every door and window, and calls for help if someone breaks in."

That sentence is packed with hidden roles and hidden decisions — who does what, when, and what happens if something goes wrong. Untangling that by writing paragraphs would get messy fast. So the requirement engineer reaches for something more precise than prose: a model.

SPEC-00REQUIREMENT MODELING
Book Definition
The process of identifying the requirements the software solution must meet, in order to be successful.
Divided into four stages
Scenario-Based Modeling · Flow-Oriented Modeling · Class-Based Modeling · Behavioral Modeling.
This chapter covers
Scenario-Based Modeling — the very first stage, where requirements become pictures of who uses the system and how.

SafeHome's requirements will eventually pass through all four modeling stages — this guide walks through the first one in full.

2 Stage One, In Full

Scenario-Based Modeling

This is where the messy sentence Mr. Rao spoke turns into a diagram everyone — customer, developer, tester — can look at and agree on.

SPEC-01SCENARIO-BASED MODELING
Invented by
Ivan Jacobson.
Modeling means
Producing diagrams — drawn using UML, the Unified Modeling Language.
Represented as
Use case diagrams and Activity diagrams.
Key terms
Use case — a scenario describing a thread of usage for a system. Actor — represents the role of a person or device in the system's functions.
The Story

Before deciding any code, the developer asks one question:

"Who will actually touch this system, and what will each of them do with it?"

For SafeHome, that list looks like:

  • Homeowner — arms it, disarms it, checks cameras
  • Door/Window Sensor — detects if something opens
  • Monitoring Service — gets alerted, calls for help

Each of these is an Actor. What each of them does with the system is a Use Case.

3 The Building Block

Use Cases — an aid, not the whole answer

A use case doesn't try to capture everything about the system. It has one narrow, useful job.

SPEC-02USE CASE
Book Definition
Use cases are simply an aid to defining what exists outside the system (actors) and what should be performed by the system.
Purpose
Identifies the possible use cases for the system and produces the use case diagrams.
4 Step One of Writing a Use Case

Creating a Preliminary Use Case

The very first draft of a use case is deliberately rough. Four questions guide how it gets written.

SPEC-03PRELIMINARY USE CASE
Guiding questions
What to write about · How much to write about it · How detailed to make the description · How to organize the description.
The Story — First Draft

The developer writes down the simplest possible version:

"Homeowner arms the system before leaving home."

That's it — one line. Rough on purpose. It's a starting point, not the final word.

5 Step Two

Refining a Preliminary Use Case

A one-line use case hides a dozen "what if" situations. Refining means chasing those down before they become bugs.

Can the actor take some other action at this point?
Is it possible the actor will encounter an error condition at some point? If so, what?
Is it possible the actor will encounter some other behavior at some point? If so, what?
The Story — Chasing the "what ifs"

What if the Homeowner types the wrong password?

→ System should ask again, and lock out after 3 wrong tries.

What if a door sensor fails to respond?

→ System should show a "sensor offline" warning instead of silently ignoring it.

What if the Homeowner arms the system but a window is still open?

→ System should warn before arming, not after.

The one-line use case has now grown into something the team can actually build and test against.

6 Step Three

Writing a Formal Use Case

Once refined, the use case is written up properly — in a fixed format everyone recognizes.

SPEC-04FORMAL USE CASE — ARM THE SYSTEM
Use Case Name
Arm the SafeHome System
Primary Actor
Homeowner
Secondary Actors
Door/Window Sensors, Monitoring Service
Description
The Homeowner arms the system before leaving the house so that any break-in triggers an alert.
Precondition
Homeowner has a valid access code. All sensors are online.
Main Flow of Events
1. Homeowner selects "Arm System" on the keypad or app.
2. System checks all doors and windows are closed.
3. Homeowner enters the access code.
4. System validates the code and arms itself.
5. System confirms "Armed" with a beep and a light.
Exception Flows
— A door/window is open → system warns before arming.
— Code entered incorrectly 3 times → system locks out and notifies Monitoring Service.
— A sensor is offline → system displays a warning instead of arming silently.

8 Drawing the Flow

Activity Diagram — what happens, in order

A use case diagram shows who. An activity diagram shows the sequence — the actual step-by-step flow inside one scenario, including the decisions.

SPEC-05ACTIVITY DIAGRAM
Book Definition
A graphical representation of the flow of interaction within a specific scenario.
Notation
Rounded rectangles imply a specific system function · Arrows represent flow through the system · Decision diamonds depict a branching decision · Solid horizontal lines indicate parallel activities occurring at the same time.
Activity Diagram — Arming the SafeHome System (decision diamond + parallel confirmation bars)
Reading the same idea elsewhere

The exact same shapes describe a room-booking flow: Guest selects dates → Decision: room available? → Yes: confirm booking / No: suggest alternate dates → Payment and confirmation happen as parallel activities. The notation doesn't change — only the scenario does.

9 Adding Responsibility

Swimlane Diagram — who owns which step

An activity diagram shows the flow. A swimlane diagram adds one more layer: which actor is responsible for each step, by placing activities into vertical lanes.

SPEC-06SWIMLANE DIAGRAM
Book Definition
Represents the flow of activities described by the use case, while at the same time indicating which actor or analysis class has responsibility for the action described by an activity rectangle.
Notation
Responsibilities are represented as parallel segments that divide the diagram vertically.
Swimlane Diagram — arming SafeHome, split across three responsibility lanes
Why this view matters

The activity diagram alone couldn't answer: "if the code validation fails, whose job is it to fix that?" The swimlane makes it obvious — validating the code is the SafeHome System's job, not the Homeowner's, and standing by for alerts belongs entirely to the Monitoring Service.

"A picture of behavior prevents a thousand misunderstandings of text."
