1 The Core Idea

A different question this time

Scenario-Based Modeling was all about the user. Flow-Oriented Modeling shifts the camera entirely.

Scenario-Based Modeling asks

WHO uses the system?

Flow-Oriented Modeling asks

HOW does information move inside the system?

SPEC-00FLOW-ORIENTED MODELING
Definition
Represents how data objects are transformed as they move through the system.
Easy Meaning
Instead of tracking the user, this approach tracks the data — where it comes from, what happens to it, where it's stored, and where it finally goes.

3 The Main Diagram

DFD — Data Flow Diagram

SPEC-01DFD
Definition
A graphical representation that shows the movement of data through a system.

Every DFD, no matter how big, is built from exactly four components. Never miss these in an exam.

1. External Entity

Definition: A person, organization, or another system that sends data to the system or receives data from it.

Symbol: Rectangle

ATM Example: Customer, Bank Server

✔ Source / Destination · Outside the system

2. Process

Definition: A process transforms input data into output data.

Symbol: Circle (bubble)

ATM Example: Verify PIN, Withdraw Cash, Update Account

✔ Transformation · Verb Phrase

3. Data Flow

Definition: Movement of information from one place to another.

Symbol: Arrow

Examples: Card Info, PIN, Account Details, Withdrawal Amount

✔ Input · Output · Movement

4. Data Store

Definition: Repository where data is stored for later use.

Symbol: Open-ended rectangle

ATM Example: Customer DB, Account DB, Transaction DB

✔ Database · Repository
4 Don't Break These

DFD Rules

A DFD isn't just "draw some shapes and arrows" — it follows strict rules, and exam questions love testing exactly these.

Rule 1 — Every process needs input AND output

✗ Wrong: Card Info → (Verify PIN) → nothing
✓ Correct: Card Info → (Verify PIN) → Verification Result

Rule 2 — Entity cannot connect directly to Data Store

✗ Wrong: Customer → Account Database
✓ Correct: Customer → (Process) → Account Database

Rule 3 — Data Store cannot connect directly to Data Store

✗ Wrong: Account Database → Transaction Database
✓ Correct: Account Database → (Process) → Transaction Database

Rule 4 — Entity cannot connect directly to Entity

✗ Wrong: Customer → Bank Server
✓ Correct: Customer → (Process) → Bank Server

In short — everything must pass through a Process. No shortcuts.

5 Getting the Labels Right

DFD Naming Guidelines

Half of drawing a correct DFD is simply naming each shape the right way.

ComponentNaming StyleExamples

And before drawing anything, these six guidelines keep every DFD clean and consistent:

01 Depict the system as a single bubble in Level 0.
02 Carefully note primary input and output.
03 Refine by isolating candidate processes and their associated data objects and data stores.
04 Label all elements with meaningful names.
05 Maintain information conformity between levels.
06 Refine one bubble at a time.
6 Level 0 DFD

At Level 0, the entire ATM system collapses into a single process. The goal here is only to show what's outside the system and what crosses its boundary — nothing about the inside yet.

7 Level 1 DFD

Opening up the single bubble

Level 0 was too general to build anything from. Level 1 breaks "ATM System" apart into its major processes — 1.0 Verify PIN, 2.0 Process Withdrawal, 3.0 Update Account — this is called functional decomposition.

Why this diagram is built in stages below: once several data flows enter the same picture, arrows can start to cross and labels can sit close together. The fix isn't to remove detail — it's to route every arrow along its own lane, and to build the picture one flow-group at a time so it's always obvious which label belongs to which arrow. Each stage below adds only the new arrows in color; everything already introduced stays visible in grey.
1

Card goes in, PIN goes out for checking

New flows: F1, F2, F3

The Customer hands over their card and PIN. Process 1.0 does not decide anything itself — it forwards the PIN onward to the Bank Server, waits for a result, and only then passes a verdict on.

F1 Customer → 1.0 : Card Info + PIN enters the system.
F2 1.0 → Bank Server : PIN Verify Request sent out for checking.
F3 Bank Server → 1.0 : Verification Result sent back (valid / invalid).
↓ next, once the PIN is verified ↓
2

Verified customer requests an amount

New flows: F4, F5

Once 1.0 has a result, it tells 2.0 whether the PIN was verified. Independently, the Customer types in how much cash they want — that request travels straight to 2.0 along its own lane, running underneath 1.0 so it never crosses the earlier PIN-checking arrows.

F4 1.0 → 2.0 : Verified Status — the go-ahead signal.
F5 Customer → 2.0 : Withdrawal Amount — how much cash is requested.
↓ next, the system checks the account itself ↓
3

The balance is checked against the database

New flows: F6, F7, F8

Now 2.0 does its real job: it asks the Account Database whether enough funds exist, reads back the current balance, and — if everything checks out — physically hands the cash back to the Customer along a separate lane below the earlier ones.

F6 2.0 → D1 : Balance Check request.
F7 D1 → 2.0 : Current Balance returned.
F8 2.0 → Customer : Cash is dispensed.
↓ finally, the account record itself must change ↓
4

The account balance is updated — complete Level 1 DFD

New flows: F9, F10 — all ten flows now shown together

2.0 hands the confirmed withdrawal details to 3.0, which is the only process allowed to write the new balance back into the database — keeping "checking" and "writing" as two clearly separate responsibilities.

F9 2.0 → 3.0 : Withdrawal Details passed along for recording.
F10 3.0 → D1 : Updated Balance is written back.

Zooming into one process even further

Take just one process from Level 1 — 2.0 Process Withdrawal — and break it down into its own smaller steps. This is refinement, one bubble at a time.

Comes After DFDs

Once data flow is mapped, Flow-Oriented Modeling also uses a Control Flow Diagram — closely related to a state diagram — to show the events and states that control when each process actually runs, rather than the data itself.

"Flow-Oriented Modeling does not focus on the user. It focuses on how data enters the system, gets processed, gets stored, and leaves the system."
