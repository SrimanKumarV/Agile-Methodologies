1Introduction

What Is Flow-Oriented Modeling?

Before drawing a single diagram, it helps to understand the question flow-oriented modeling is really answering.

CONCEPT

Flow-Oriented Modeling

① Story

Imagine you walk up to an ATM. You insert your card, enter your PIN, enter an amount, and receive money.

How did the ATM know your balance? How did it verify your PIN? How did it update your account afterward?

Every one of those questions has the same answer.

Because information — data — was moving between the customer, the machine, and the bank.
② Intuition

Some diagrams describe a system by asking "who does what" (actors and their goals). Flow-oriented modeling asks a different question entirely: "what data moves, and how does it change shape as it moves?" It follows the data — not the user — from the moment it enters the system to the moment it leaves.

③ Definition
Flow-Oriented Modeling represents the way data objects are transformed as they move through a system — tracing input, processing, storage, and output.
④ Example

ATM trace — what actually moves:

  • Card Number → enters the system
  • PIN → sent for verification
  • Amount Requested → sent for processing
  • Balance → read from and written back to storage
  • Cash → produced as final output

Card Number, PIN, Amount, and Balance are all data — this is exactly what flow-oriented modeling tracks.

⑤ Correct Representation

Every flow-oriented system reduces to this pipeline: Input → Processing → Storage → Output.

⑥ Common Errors
✕Confusing flow-oriented modeling with scenario-based modeling (they answer different questions — see the comparison in Section 9).
✕Describing the ATM story in terms of "steps the customer performs" instead of "data that moves" — this is a Use Case answer, not a DFD answer.
⑦ Summary
✓Flow-oriented modeling = tracking the movement of DATA through a system.
✓Memory trick — Use Case Diagram asks WHO; DFD asks HOW (data moves).
2The Diagram

Data Flow Diagram (DFD)

Once we know we're tracking data, we need a notation to draw it. That notation is the DFD.

CONCEPT

Data Flow Diagram

① Story

Suppose you had to explain the ATM to someone using only boxes, circles, and arrows on a whiteboard — no sentences allowed. You'd naturally draw the customer as a box, the "verify PIN" activity as a bubble, the arrow between them as the PIN itself moving, and the account records as a filing cabinet. That whiteboard sketch is a DFD.

② Intuition

A DFD is simply a map of data in motion. It deliberately hides control logic, timing, and decision conditions — it only cares about what data exists, where it comes from, what transforms it, where it is stored, and where it finally goes.

③ Definition
A Data Flow Diagram (DFD) is a graphical representation that depicts the flow of information through a system.

Purpose of a DFD:

  • Understand the movement of data
  • Identify inputs and outputs
  • Understand processing
  • Identify data storage
  • Improve overall system design
④ Example

For the ATM: Customer, ATM System, and Bank Server exchange Card Info, PIN, Amount, Balance, and Cash — this whole exchange, drawn with standard symbols, is the DFD you will build section by section below.

⑥ Common Errors
✕Treating a DFD like a flowchart and adding decision diamonds or loops — DFDs have no control-flow symbols.
✕Showing timing or sequence numbers on the arrows themselves — a DFD shows what flows, not when.
⑦ Summary
✓DFD = a picture of data movement, built from exactly four symbol types (next section).

The Four Components of a DFD

Every DFD, at any level, is built from only these four symbols.

1 · External Entity

Rectangle · a person, organization, or system outside the boundary that supplies or receives data.

Naming: Noun (Customer, Bank, Admin)

2 · Process

Circle / bubble · transforms incoming data into outgoing information. Must always have an input and an output.

Naming: Verb + Noun (Verify PIN)

3 · Data Flow

Arrow · the movement of information from one component to another.

Naming: Data name (PIN, Amount)

4 · Data Store

Open rectangle · a repository where information is stored for later use.

Naming: Noun (Account Database)

CONCEPT

Putting the Four Symbols Together

① Story

The customer hands over a PIN. Somewhere, a process checks it against the account records, and a result comes back.

② Intuition

Notice the shape of that sentence: entity → process → store, with an arrow (a data flow) connecting each pair. That three-symbol chain is the atomic building block of every DFD you will ever draw.

③ Definition
A complete, valid data flow always connects an External Entity, a Process, or a Data Store to another of these — never entity-to-entity and never store-to-store directly.
⑤ Correct DFD — Minimal Chain

Customer → 1.0 Verify PIN → Account Database — the atomic entity–process–store chain.

⑥ Common Errors
✕Drawing an arrow straight from Customer to Account Database, skipping the process — covered formally as Rule 2 below.
✕Labeling a data flow with a verb (e.g. "Sends PIN") instead of the data itself (e.g. "PIN") — flows are named after data, not actions.
⑦ Summary
✓Four symbols only: External Entity (rectangle), Process (circle), Data Flow (arrow), Data Store (open rectangle).
✓Everything in a DFD must pass through a process — this is the golden rule behind Section 4.

5Levels of DFD — Level 0

Context Diagram (Level 0)

The zoomed-out view: the entire system as a single process.

LEVEL 0

Context Diagram — ATM System

① Story

If you had ten seconds to describe the ATM to a stranger with a single circle and two boxes, what would you draw? One bubble labelled "ATM System," a Customer box on one side, a Bank Server box on the other, and arrows showing what crosses the boundary.

② Intuition

Level 0 deliberately hides everything internal — no PIN-checking logic, no database. It only answers: what is the system boundary, and what crosses it?

③ Definition
The Context Diagram represents the entire system as one single process and shows its interaction with external entities. It shows the system boundary, the external entities, and the inputs/outputs — but never internal processes or data stores.
④ Example

Customer sends Card Info / PIN and receives Cash / Receipt. ATM System queries Bank Server for Account Query and receives Balance / Approval in return. Only ONE process bubble is allowed at this level.

⑤ Correct DFD — Context Diagram
External Entity Process (single bubble) Data Flow

Level 0 — one process bubble, two external entities, no internal detail, no data store.

⑥ Common Errors
✕Showing the Account Database inside the context diagram — data stores never appear at Level 0.
✕Drawing more than one process bubble — Level 0 must contain exactly one.
✕Forgetting a return flow — every input from an entity should have a corresponding output back, where applicable.
⑦ Summary
✓Context Diagram = system as ONE process + its external entities + boundary-crossing data flows only.
✓Exam definition: "Context Diagram represents the system as one single process and shows interaction with external entities."
6Levels of DFD — Level 1

Level 1 DFD

Open up the single Level 0 bubble into its major sub-processes.

LEVEL 1

Level 1 DFD — ATM System

① Story

"ATM System" is too vague to build software from. A developer would immediately ask: verify the PIN how? Process the withdrawal how? Level 1 answers exactly that by breaking the single bubble into its major functional steps.

② Intuition

Level 1 is obtained through functional decomposition — splitting one large process into the smaller processes it is actually made of, while keeping the same external entities and the same boundary as Level 0.

③ Definition
Level 1 DFD decomposes the single process of Level 0 into its major sub-processes, introducing data stores and the movement of data between them.

Functional decomposition: the process of breaking one large process into smaller processes.

④ Example

ATM System (process 0) decomposes into 1.0 Verify PIN, 2.0 Process Withdrawal, and 3.0 Update Account, now working with an Account Database and still talking to the Customer and Bank Server exactly as Level 0 promised.

⑤ Correct DFD — Level 1
External Entity Process Data Store Data Flow

Level 1 — three numbered sub-processes, one data store, same two external entities carried over from Level 0.

⑥ Common Errors
✕Dropping the Customer or Bank Server entity that appeared in Level 0 — every Level 1 diagram must preserve all Level 0 boundary flows (this is the balancing rule, Section 8).
✕Numbering processes out of order, or reusing "1.0" for two different processes.
✕Connecting Account Database directly to Customer — still illegal at Level 1 (Rule 2 applies at every level).
⑦ Summary
✓Level 1 = functional decomposition of Level 0's single process into its numbered major processes.
✓Why Level 1? Because Level 0 is too general to design or build from.
7Levels of DFD — Level 2

Level 2 DFD

Zoom into exactly one Level 1 process and expand it further.

LEVEL 2

Level 2 DFD — Decomposing "2.0 Process Withdrawal"

① Story

"2.0 Process Withdrawal" is still hiding detail. What actually happens inside it? The balance is checked, the amount is verified against it, and only then is cash dispensed. Level 2 draws exactly that.

② Intuition

Level 2 does not re-explain the whole system — it takes one single process from Level 1 and expands only that one. Every other Level 1 process stays exactly as it was.

③ Definition
Level 2 DFD further decomposes one process from Level 1 into its own detailed sub-processes.
④ Example

2.0 Process Withdrawal expands into 2.1 Check Balance → 2.2 Verify Amount → 2.3 Dispense Cash, reading and writing the Account Database and finally returning Cash to the Customer.

⑤ Correct DFD — Level 2
External Entity Process Data Store Data Flow

Level 2 — the internal detail of process 2.0 only: 2.1 → 2.2 → 2.3, all numbered under their parent process.

⑥ Common Errors
✕Also expanding 1.0 Verify PIN or 3.0 Update Account inside this same diagram — Level 2 explains only ONE parent process at a time.
✕Numbering the sub-processes 1, 2, 3 instead of 2.1, 2.2, 2.3 — the numbering must show which parent process they belong to.
✕Losing the Account Database connection that existed at Level 1 for process 2.0 — sub-processes must still touch every store/entity the parent touched.
⑦ Summary
✓Level 2 explains ONE Level-1 process in detail — not the whole system.
✓Numbering convention: parent 2.0 → children 2.1, 2.2, 2.3 …

How the Three Levels Connect

LEVEL 0 — Whole System

  • 0 ATM System

LEVEL 1 — Major Processes

  • 1.0 Verify PIN
  • 2.0 Process Withdrawal
  • 3.0 Update Account

LEVEL 2 — Detailed Process

  • 2.1 Check Balance
  • 2.2 Verify Amount
  • 2.3 Dispense Cash

Memory trick: Level 0 = Whole System · Level 1 = Major Processes · Level 2 = Detailed Process.

8Consistency Rule

Balancing Between Levels

A DFD set is only correct if every level agrees with the one above it.

RULE

The Balancing Rule

③ Definition
Balancing means every data flow entering or leaving a parent process at one level must reappear, in total, among the flows entering or leaving its child processes at the next level.
④ Example

Level 0 shows Customer ↔ ATM (Card Info/PIN in, Cash/Receipt out). Level 1 must still show a Card+PIN flow reaching the Customer boundary and a Cash flow leaving it — it does, via 1.0 and 2.0.

⑥ Common Errors
✕Introducing a brand-new external entity at Level 1 that never appeared at Level 0.
✕Silently dropping a boundary flow when decomposing — this breaks balancing even if the diagram still "looks" complete.
⑦ Summary
✓Child-level diagrams must preserve every parent-level boundary flow — nothing added, nothing dropped.
