Getting Started

Why do we need a "Process" at all?

Before jumping into definitions, picture something you already understand — building a house.

🏠 The House-Building Analogy

You never plaster the walls before laying the foundation, and you never fit the roof before the walls exist. Construction always follows a natural order: foundation → walls → roof → interiors.

Software is no different. Whether you're building a food delivery app or a hospital management system, every project quietly passes through the same broad stages. That common skeleton — the one thing every software project shares — is called the Generic Process Framework.

Core Concept

The Generic Process Framework

A small number of broad activities that apply to every software project, no matter its size or domain.

Definition A software process is a framework for the activities, actions, and tasks required to build high-quality software. The Generic Process Framework defines 5 framework activities, supported throughout by a set of umbrella activities.

Umbrella Activities sit "above" all five Framework Activities and support them continuously
1

Communication

🗣️

Heavy interaction with the customer to gather requirements and understand the real problem, before writing any code.

  • Meetings & interviews with stakeholders
  • Understanding business objectives
  • Collecting requirements
Example: A hospital asks for "Patient Management Software." The team talks to doctors, receptionists, and lab staff first — otherwise they might build a system only doctors can use, missing what receptionists actually need.
2

Planning

🗺️

Creates a "map" for the project — the tasks to do, risks involved, resources required, and the work schedule.

  • Estimation (time, cost, effort)
  • Scheduling (timeline, milestones)
  • Risk analysis
Example: Like planning a road trip before driving — deciding the route, fuel stops, and budget — the team decides how many developers are needed and by when each module will be ready.
3

Modeling

🧩

Sketching a "blueprint" of the software — understanding what it must do (analysis) and how it will be built (design).

  • Analysis Model — requirements
  • Design Model — architecture, data, UI
Example: For a Library System — deciding database tables (Book, Student, Issue-Record) and screens (Search Page, Issue Page) before any coding begins.
4

Construction

🛠️

Combines code generation with testing needed to uncover errors — this is where the software is actually "built."

  • Coding — writing the program
  • Testing — unit & integration testing
Example: Writing the actual "Issue Book" function, then repeatedly testing it with different inputs to make sure it never crashes.
5

Deployment

🚀

The complete (or partially complete) product is delivered to the customer, who evaluates it and gives feedback.

  • Installation / release
  • User training
  • Feedback collection
Example: The Library System is installed on the college server; librarians are trained; feedback like "Return Book button is hard to find" feeds into the next update.

Getting Specific

📋 Task Set

Each Framework Activity is broad. A Task Set breaks it down into the actual, specific work to be done.

Definition A Task Set defines the actual work to accomplish a framework activity's objectives — it includes a list of tasks to be done, a list of work products to be produced, and a list of quality assurance filters to be applied.

🪶 Small / Simple Project

A light task set is enough:

  • Quick call with the client
  • Short notes of requirements
  • Informal confirmation

🏛️ Large / Critical Project

A heavy task set is needed:

  • Formal stakeholder meetings
  • Detailed requirement documents
  • Sign-off approvals

Key idea: the Framework Activity stays the same across every project — only the Task Set changes, based on the size and criticality of the project. This is what makes the framework "generic" yet flexible.

Sequencing the Work

🔀 Process Flow

Process Flow describes how the framework activities — and the tasks within them — are organized with respect to sequence and time.

Linear

Straight-line flow

All 5 activities happen once, in order. Best for small, fully-understood projects.

Iterative

Repeats & refines

The full cycle repeats, refining the product each time. Great when the customer wants changes after seeing a version.

Evolutionary

Spiral, growing completeness

Activities repeat in a spiral, each pass producing a more complete version of the software.

Parallel

Simultaneous activities

Independent tasks (like UI design and database design) run at the same time to save overall project time.

Chapter 4

📉 The Waterfall Model

Just like a real waterfall, water flows downward step-by-step — never backward. Each phase must fully finish before the next begins.

💧 Quick Facts

First formally described by Winston W. Royce in 1970. It is the first and simplest process model ever introduced — also called the Linear-Sequential Life Cycle Model. Phases never overlap: a phase begins only after the previous one is fully complete.

Each phase cascades into the next — like steps of a waterfall — with no going back
1

Requirement Analysis

All possible requirements are gathered and documented completely, up front.

📌 For a College ERP: attendance, marks, fees, library — everything is listed before any design starts.
2

System Design

Requirements are studied and a complete design (architecture, database, screens) is prepared.

📌 Deciding the database tables (Student, Attendance, Marks) and overall architecture.
3

Implementation (Coding)

Code is written strictly based on the design, usually as small units.

📌 Developers code the Attendance module exactly as per the design document.
4

Testing

All units are integrated and tested together as a complete system.

📌 Checking that marking attendance correctly reflects in the reports module.
5

Deployment

The finished, tested product is delivered and installed at the customer's site.

📌 The ERP goes live on the college servers for staff and students.
6

Maintenance

Issues found in live use are fixed, and small enhancements are made.

📌 A bug allowing marks above 100 is discovered and fixed after a month of use.
Golden Rule You must fully complete one phase before moving to the next — there is no going back. If a misunderstood requirement is discovered during Testing, the entire waterfall must restart from the top. This is the model's biggest weakness.

✅ Advantages

  • Very simple and easy to understand and use
  • Each phase has clear deliverables and a review process
  • Best suited when requirements are well understood and fixed
  • Easy to manage due to the rigidity of the model
  • Clear milestones, so progress is easy to track

⚠️ Disadvantages

  • No working software until very late in the life cycle
  • High risk if requirements change midway
  • Not suitable for complex or long-running projects
  • Poor fit when requirements may change moderately-to-highly
  • Real projects rarely follow such a strict sequential flow
Clear RequirementsRequirements are well understood and unlikely to change.
Stable TechnologyThe technology being used is familiar and stable.
Short, Fixed ScopeThe project is short with a clearly fixed scope — e.g. a basic payroll calculator with fixed rules.
Chapter 5

📶 The Incremental Model

Also known as the Multi-Waterfall Model — requirements are broken into standalone modules, each delivered as a usable increment.

🏗️ The Growing House Analogy

Instead of building an entire house before anyone can live in it, you build one room first — the family moves in. Then you add a second room, then a kitchen, then a garden. At every stage, there's a usable part of the house, and it keeps getting bigger.

Incremental development goes through the same steps every time — analysis → design → implementation → testing → maintenance — but repeats them for each increment.

The Incremental Model — a staggered series of mini-waterfalls, each adding new functionality
IncrementFeatures Delivered — College ERP Example
Increment 1Student login + Attendance module (core, usable product)
Increment 2+ Marks module added
Increment 3+ Fee payment module added
Increment 4+ Library module + Notifications added

Notice: after Increment 1 alone, the college already has a working piece of software — even though the full ERP isn't finished yet. That's the biggest strength of this model.

Key Characteristics Each iteration passes through requirements, design, coding, and testing. Every subsequent release adds function to the previous one, until all designed functionality is implemented. The system is put into production as soon as the first increment is delivered — and once the client evaluates the core product, planning begins for the next increment.

✅ Advantages

  • Working software is generated early — from the first increment itself
  • Customers can use and review each increment, shaping future ones
  • Lower risk of complete project failure — problems surface early
  • Smaller increments are easier to test and debug
  • Flexible — future increments can absorb changing requirements

⚠️ Disadvantages

  • Requires good planning to properly divide the system into increments
  • Total cost can exceed Waterfall if not managed well
  • Each increment must integrate cleanly without breaking earlier ones
  • Not ideal if the problem can't be split into independent pieces

🧭 When to Use the Incremental Model

Requirements are ClearThe core system requirements are clearly understood upfront.
Early Release NeededThere's demand for an early release of a working product.
Less-Skilled TeamThe software engineering team isn't very well trained — smaller pieces are easier to manage.
High-Risk Features InvolvedHigh-risk goals can be tackled in an early increment to reduce overall project risk.
Wrapping Up

Waterfall vs. Incremental — At a Glance

Waterfall ModelIncremental Model
DeliveryEntire software delivered at the endDelivered in usable increments
Customer FeedbackOnly after full completionAfter every increment
RiskHigh if requirements changeLower — issues caught early
FlexibilityRigid, hard to change mid-wayAdapts as increments progress
Best ForSmall, well-defined, unchanging projectsLarger projects with evolving needs
Working SoftwareOnly at the very endFrom the first increment onward

🎯 Big-Picture Recap

Generic Process FrameworkEvery project shares 5 activities — Communication, Planning, Modeling, Construction, Deployment — continuously supported by Umbrella Activities.
Task SetBreaks each framework activity into specific tasks, work products, and QA checkpoints — scaled to project size.
Process FlowThe pattern in which activities occur — Linear, Iterative, Evolutionary, or Parallel.
Waterfall ModelStrict linear flow — one phase fully finishes before the next begins. Best for small, fixed-scope projects.
Incremental ModelRepeats the framework in stages, delivering usable software early and often — best for evolving, larger projects.
