Requirement Engineering,
told through the College Canteen App

The Principal has a complaint: students are stuck in long canteen queues every single day. Before anyone opens a code editor, that one complaint has to travel through seven well-defined tasks. Follow it end to end, one task at a time.

🍽️ Long canteen queues ⏱️ Students waiting too long 📋 No clear feature list yet 💰 Only ₹50,000 budget
1 The Core Idea

"Can we directly start coding?"

That's the very first question worth asking about any software project — including this one.

The Story

The Principal says:

"Students are standing in long queues in the canteen."

Can we directly start coding a solution? No.

Ask: "Then what should we do first?" The expected answer: "We should know what the customer wants." That entire discovery process — before a single line of code — has a name.

REBook Def.
Requirement Engineering
Book Definition
The process of establishing the services that the customer requires from a system, and the constraints under which it operates and is developed.
Easy Meaning
Before writing even one line of code, know: what should the software do, who will use it, and what restrictions exist.

3 Task One

Inception 💡 — "What exactly is the problem?"

Before anything else, the team builds a basic understanding of the problem itself, who wants it solved, and how well everyone is communicating so far.

01Book Def.
Inception
Book Definition
Establish a basic understanding of the problem, the people who want a solution, the nature of the solution, and the effectiveness of communication.
Requirement engineer must
Identify stakeholders · recognize multiple viewpoints · work toward collaboration · break the ice and start communication.
The Story

Q: What is the problem?

A: Long waiting time.

Q: Why do we need the app?

A: To reduce waiting time.

Q: Who is involved?

A: Students, Canteen Staff, Principal.

These people are called Stakeholders — people who are affected by or interested in the system.

4 Task Two

Elicitation 🎤 — "What do you actually want?"

Now the team draws the actual requirements out of everyone who has a stake in the app.

02Book Def.
Elicitation
Book Definition
Draw out requirements from customers, users, and other stakeholders.
What can go wrong
Problem of scope · Problem of understanding · Problem of volatility. The fix: gather requirements in an organized way.
The Story

"What features do you need?"

Students say: View menu · Order food · Online payment

Canteen staff say: Update menu · View orders

Principal says: Daily reports

Each of these is a Requirement — a condition or capability needed by a user to solve a problem.

Every requirement gathered here falls into one of three buckets:

Functional

What the system should do
  • Login
  • Place Order
  • Pay Online

Non-Functional

How the system should work
  • Response within 2 seconds
  • Secure payment
  • Easy to use

Constraints

Restrictions on the project
  • Budget ₹50,000
  • Android only
  • Finish in 2 months
5 Task Three

Elaboration 🔍 — "Tell me exactly what you mean"

Raw requirements are still too vague to build from. Elaboration turns "I want online payment" into something a developer can actually implement.

03Book Def.
Elaboration
Book Definition
Create an analysis model that identifies data, functions, and behavioral requirements — a refined technical model of software functions, features, and constraints.
How it's done
Use cases are developed · domain classes identified · state machine diagrams used.
The Story

"I want online payment."

Ask: UPI? Debit card? Credit card?

"I want order history."

Ask: Last 5 orders? Last 10 orders?

Now the requirement is no longer vague — it is detailed enough to build.

6 Task Four

Negotiation 🤝 — "We can't build everything"

Wish lists are always bigger than budgets. This task is where reality and ambition sit down together.

04Book Def.
Negotiation
Book Definition
Customers and developers negotiate to agree on a realistic set of requirements — ranking priority, assessing cost and risk, and resolving internal conflicts.
Easy Meaning
Not every requirement can be implemented. Compromise is needed.
The Story

Students: "Add AI Recommendation."

Principal: "Budget is only ₹50,000."

Developer: "Impossible — for now."

Version 1 ships with: ✔ Ordering · ✔ Payment · ✔ Menu Display. The AI feature is deferred to a later version.

7 Task Five

Specification 📄 — "Write it all down"

Everything agreed upon so far now needs to exist somewhere other than people's memories.

05Book Def.
Specification
Book Definition
Requirements are documented in a form that can be reviewed and approved. Can be a written document, a set of models, a formal mathematical model, use-case scenarios, or a prototype.
The Story

Login, Menu, Order, Payment — everything gets written down. Why? Because people forget discussions. The document becomes proof.

This document is called the SRS — Software Requirement Specification: a document that describes the complete behavior and requirements of the software, containing Functional Requirements, Non-Functional Requirements, Constraints, and Interfaces.

The SRS is usually built using three modeling tools:

🔀

Data Flow Diagram (DFD)

Shows how data flows through the system, from input to processing to output.

📖

Data Dictionary

A repository storing information about every data item that appears inside the DFDs.

🔗

Entity-Relationship (E-R) Diagram

A logical representation of data using entities, relationships, and their attributes.

8 Task Six

Validation ✔️ — "Is this actually right?"

A written document can still be wrong. Validation is the quality gate before development truly begins.

06Book Def.
Validation
Book Definition
Examine the specification to ensure that all requirements have been stated unambiguously, and that inconsistencies have been detected and errors corrected.
Looks for
Errors in content or interpretation · missing information · inconsistencies · conflicting or unrealistic requirements.
The Story — a conflict caught

Requirement 1: "System works only inside college."

Requirement 2: "Students can order from home."

These two directly contradict each other — the requirement is inconsistent and needs correction before development starts.

Every requirement is checked against this list:

Correct
Complete
Consistent
Unambiguous
Feasible
Verifiable

Formal techniques used to validate:

Reviews / Inspections

  • Systematic manual analysis of the requirements.

Prototyping

  • An executable model checks requirements in practice.

Test-Case Generation

  • Tests are built to check that each requirement is testable.
9 Task Seven

Requirement Management 🔄 — "It never really stops"

Shipping the app doesn't end the story. Requirements keep changing, and someone has to track it all.

07Book Def.
Requirement Management
Book Definition
Helps the project team identify, control, and track requirements and changes to requirements as the project proceeds.
The Story

One month later — Students: "Add coupon feature."

Principal: "Add QR payment."

Requirements have changed. The SRS now needs to be updated to match.

⭐ Scope Creep — the trap to watch for

"Just one more feature."

"Just one more requirement."

"Just... one more."

Requirements keep increasing, uncontrolled, after the project has already started. This pattern is called Scope Creep — the uncontrolled addition of requirements after the project starts. Requirement Management exists specifically to keep it in check.

"If requirements are wrong, even perfect coding will produce the wrong software."
✚ A Complementary Lens

The Requirements Analysis Process

Alongside the seven tasks above, the same underlying work is often described as five practical steps — useful for exam answers that ask for "the requirements analysis process" specifically.

1

Identify Key Stakeholders & End-Users

Find the main sponsors of the project — they have final say on scope — then the end-users, since the product exists to satisfy their needs.

2

Capture Requirements

Ask each stakeholder and end-user for their requirements, using one-on-one interviews, focus groups, use cases, and prototypes.

3

Categorize Requirements

Group requirements to avoid confusion — see the menu board below for the four categories.

4

Interpret & Record Requirements

Determine what's actually achievable and document it — by defining requirements precisely, prioritizing them, running impact analysis, resolving conflicts, and analyzing feasibility.

5

Sign Off

Get a signed agreement from key stakeholders once the final decision is made — so the scope can't quietly grow out of control later.

— Today's Requirement Menu — Four Counters —

Functional Requirements

Functions the product is required to perform — e.g. placing an order.

Technical Requirements

Technical issues to consider for successful implementation — e.g. which payment gateway API to use.

Transitional Requirements

Steps required to implement the new product smoothly — e.g. migrating from the old paper token system.

Operational Requirements

Backend operations needed for the product to function properly — e.g. syncing daily sales reports.

✓ Why All This Matters

Without Requirement Engineering

Wrong software gets built · costs increase · projects get delayed · customers end up dissatisfied. Every one of the seven tasks above exists to prevent exactly these four outcomes.
