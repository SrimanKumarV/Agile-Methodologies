1OVERVIEW

The XP Process — Overview

Definition The XP process is a continuous, iterative cycle in which the customer explains requirements, the team plans a small amount of work, designs and codes it, tests it, obtains feedback, and uses that feedback to improve the next iteration.

In short:

Plan
→
Design
→
Build
→
Test
→
Get Feedback
→
Improve
↺
Repeat

The XP life cycle consists of five main activities:

Process ActivityMain Question It Answers
PlanningWhat should we build next?
DesigningHow should we structure the solution?
CodingHow do we implement it?
TestingDoes it work correctly?
Feedback LoopsWhat did we learn, and what should change?
Note Feedback is not the end point of XP — it becomes an input to the next iteration. The cycle never truly "finishes" until the product itself is complete; each pass around the loop only makes the product a little more complete and a little better understood.
2STAGE 1

Planning

Definition Planning in XP is the activity of deciding which valuable functionality should be developed next, estimating the required effort, and adjusting the plan according to time, resources, priorities, and new information.

Why is planning needed?

XP deliberately avoids predicting the entire project in detail at the start. Instead, a large requirement is broken down and worked through gradually:

Large Requirement
→
Small User Stories
→
Select Important Stories
→
Estimate
→
Plan Small Iteration

Planning has three parts

2.1PLANNING · PART A

Exploration

Definition Exploration is the initial discussion in which the customer explains the desired functionality and programmers investigate and estimate the effort required to implement it.

What the Customer does

  • Explains requirements
  • Describes desired behaviour
  • Provides domain information
  • Creates or refines User Stories

What the Programmer does

  • Understands the requirement
  • Identifies the technical work involved
  • Estimates effort and time
  • Raises technical concerns early
Attendance system example Customer: "Students should be able to see their attendance percentage."
Programmer: "We estimate that this functionality requires approximately two days."
Note Exploration = Customer defines WHAT + Programmer estimates HOW MUCH effort.
2.2PLANNING · PART B

Planning (the negotiation)

Definition Planning is the negotiation between business/customer priorities and technical estimates, used to select realistic work for an iteration or release.

Business considers

  • Priority
  • Scope
  • Business value
  • Release needs
  • Important dates

Technical team considers

  • Effort
  • Technical difficulty
  • Risks
  • Available resources
  • Development sequence
Attendance system example The customer would like all five of the following: (1) Faculty Login, (2) Mark Attendance, (3) Student Attendance View, (4) Shortage Alert, (5) Attendance Analytics — but the team can only deliver two major features in the current iteration.

The customer chooses: Mark Attendance and Student Attendance View. The iteration is planned around exactly those two features.
2.3PLANNING · PART C

Steering

Definition Steering is the continuous adjustment of the XP plan through small corrective decisions as new information becomes available — described in XP as "influencing the process by little moves."

Why is steering required?

The original plan is built on estimates, and actual development often reveals things the estimate could not have known: unexpected technical difficulty, new requirements, schedule problems, or simply an incorrect estimate. XP responds by adjusting the plan rather than rigidly following the original one.

The four steering moves

1. Iteration

Small development cycle

Plan and execute a short development cycle, one at a time.

Iteration 1 → Mark Attendance. Iteration 2 → Student Attendance View. Iteration 3 → Shortage Alert.

2. Recovery

Get the project back on track

Adjust the plan when the team is falling behind.

The attendance report was estimated at 3 days, but technical difficulties cause a delay. The team reduces current scope, moves a lower-priority story, or adjusts the schedule: Plan → Delay discovered → Recovery → Adjusted plan.

3. New Story

New requirement → new story

A newly discovered requirement is captured as a new User Story rather than being squeezed into existing work.

Initially: "Students can view attendance." Later, the customer adds: "Students should receive an alert if attendance falls below 75%." → New Requirement → New User Story → Future Iteration.

4. Re-estimation

Revise the estimate based on new information

An earlier estimate is corrected once actual experience reveals better information.

Biometric integration was estimated at 2 days. After investigation, it needs additional API work, so the estimate is revised: Original Estimate → Actual Experience → New Information → Re-estimation.
2.4PLANNING · KEY CONCEPT

The Planning Game

Definition The Planning Game is an XP planning activity in which business people decide priorities and scope while technical people provide estimates and technical consequences, allowing both sides to negotiate a realistic development plan.

Neither business considerations nor technical considerations are treated as dominant on their own — software development is an evolving dialogue between the possible (what the team can actually build) and the desirable (what the business wants).

Business people decide

  • Scope — how much of the problem must be solved for the system to be valuable?
  • Priority — which feature matters more?
  • Composition of releases — which features belong in a release?
  • Dates of releases — when should useful software be available?

Technical people decide

  • Estimates — how long will a feature take?
  • Consequences — what technical outcomes follow from a business decision?
  • Process — how should the work and team be organized?
  • Detailed scheduling — which stories should be built first?
Note Business decides WHAT and PRIORITY. The technical team provides ESTIMATES and the technical implications of those choices. The result of the negotiation is a realistic plan both sides can commit to.
3STAGE 2

Designing

Definition Designing in XP is the lightweight preparation of the solution structure for the selected iteration, using simple collaborative design techniques and small experiments to reduce uncertainty — rather than a heavy up-front design document.

CRC Cards

Class — Responsibility — Collaboration. CRC Cards are a lightweight object-oriented design technique representing classes, their responsibilities, and their collaborators, letting the whole team contribute design ideas together.

Reading the card

  • Class — what object or class is involved?
  • Responsibility — what should the class do?
  • Collaboration — which other classes does it work with?

CRC cards are written and discussed by the whole team, so the final design reflects the group's best ideas rather than a single person's assumptions.

Spike Solutions

Definition A Spike Solution is a small, focused technical experiment used to investigate uncertainty or risk before committing to the complete implementation — it ignores every concern except the one specific question being tested.
Attendance system example Question: "Can we retrieve attendance data from the biometric device?" Instead of building the entire integration, the team runs a small experiment (the spike), learns what's technically possible, and only then decides how to proceed.
Note A spike is an experiment, not a complete product. Its only purpose is to answer one uncertain technical question as cheaply as possible.
4STAGE 3

Coding

Definition Coding is the implementation of the selected user stories using XP programming practices, while continuously maintaining code quality and integrating changes. XP treats coding as the most important phase of its life cycle, prioritizing real working code over documentation.

Coding in XP is supported by a set of practices working together:

Simple Design

Build only what today's requirement needs; remove extra complexity as soon as it's found.

TDD

Write the test before the code that satisfies it.

Pair Programming

Two programmers, one machine, continuous review.

Refactoring

Improve the internal structure of code without changing its behaviour.

Collective Ownership

Any developer can change any part of the codebase at any time.

Coding Standards

Shared naming and formatting rules keep the code consistent and readable.

40-Hour Week

Sustainable pace keeps the team rested, focused, and motivated.

Test-Driven Development (TDD)

Attendance system example Requirement: calculate attendance percentage. Input: present = 8, total = 10; expected = 80%.
First the test is written with the expected result of 80% — it initially fails because no code exists yet. Minimal code is then written: 8 / 10 × 100 = 80. The test passes, and the code is refactored if needed.
NoteTDD = test first, code second.

5STAGE 4

Testing

Definition XP integrates testing with development instead of leaving it entirely until the end. All code must pass its unit tests before it is considered complete, and the finished feature is checked again against the customer's own acceptance tests.

Unit Tests

Checks a small piece of code in isolation. All unit tests must run flawlessly for development to continue.

calculateAttendance() — input 8/10 → expected output 80%.

Customer Acceptance Tests

Checks whether the completed functionality satisfies the customer's specification. Run once coding is complete, and demonstrated to the customer.

Student logs in → views attendance → correct percentage displayed → PASS.
6STAGE 5

Feedback Loops

Definition A feedback loop is a short cycle in which the team develops functionality, obtains information from testing, customers and team interaction, learns from that information, and adjusts subsequent development.

Three levels of feedback

Short Iterations

XP deliberately keeps iterations very short — often a weekly cycle — because the earlier a problem is discovered, the cheaper it is to fix.

Long feedback loopXP's short feedback loop
Requirement → 6 months of building → complete system shown to customer → "Actually, I wanted something different" → very expensive to correct Requirement → small feature → 1 week → customer feedback → correction → next feature → much cheaper to correct
Attendance system — weekly cycle Week 1: build faculty login → feedback: "use faculty ID, not email" → adjusted.
Week 2: build attendance entry → feedback: "we also need to edit attendance" → adjusted.
Week 3: build the attendance report → cycle continues.

Osmotic Communication

When the team sits together, useful information travels naturally — team members overhear conversations relevant to their own work without any formal meeting being called.

Example Developer A says aloud: "the attendance API is returning an incorrect value." Developer B, sitting nearby, overhears and replies: "I hit that yesterday — check the date format." No meeting was needed for this fix to happen.

Bottlenecks and Improvement

As the team communicates more and receives continuous feedback, it starts noticing bottlenecks in how it builds software — and learns, together, to work around them.

Coding
→
Testing takes too long
→
Bottleneck identified
→
Team changes approach
→
Faster testing

Without short feedback loops, a bottleneck like this might only surface much later — after far more time and work has already gone into it.

7PUTTING IT TOGETHER

Complete Worked Example — College Attendance System

Every concept above is traced here as one connected story, from a single customer request through a full turn of the XP cycle.

Requirement Customer: "Students should be able to see their attendance percentage."
StageWhat happens
Planning — ExplorationCustomer explains: "Student should see attendance percentage." Programmer estimates the effort.
Planning — Planning GameCustomer prioritizes attendance viewing over a less important analytics feature.
Planning — SteeringDuring development: a new requirement appears (New Story); the estimate changes (Re-estimation); the team falls behind (Recovery); the next cycle is planned (Iteration).
DesigningDevelopers create a CRC card: Student → View Attendance → Attendance. Since biometric integration is uncertain, they run a Spike.
CodingProgrammers use Simple Design, TDD, Pair Programming, Coding Standards, Collective Ownership, and Refactoring.
TestingUnit test: 8 / 10 × 100 = 80%. Acceptance test: student logs in → views attendance → correct percentage displayed → PASS.
FeedbackCustomer: "Please also show the number of absent classes."
Next IterationNew story: "Student should see the number of absent classes." The cycle repeats.

Summary

Note — how to structure a full explanation of the XP process Introduction: Extreme Programming is an iterative Agile development approach. Its process consists of Planning, Designing, Coding, Testing and Feedback Loops. These activities repeat through short iterations so that customer and technical feedback continuously shape subsequent development.

Diagram: Planning → Designing → Coding → Testing → Feedback → Next Iteration ↺

Explain each stage with its sub-concepts (Planning: Exploration, Planning, Steering, Planning Game · Designing: CRC Cards, Spike Solutions · Coding: Simple Design, TDD, Pair Programming, Refactoring, Collective Ownership, Coding Standards · Testing: Unit Tests, Customer Acceptance Tests · Feedback Loops: Short Iterations, Customer Feedback, Test Feedback, Team Reflection, Bottleneck Identification, Improvement).

Conclusion: The distinguishing feature of the XP process is its short, continuous feedback cycle. Instead of waiting until the end of development to discover problems, XP obtains feedback throughout development and uses it to guide the next iteration.
