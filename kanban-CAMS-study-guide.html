01 Kanban Basics

Definition (Exam Point)

Kanban is a method for process improvement used by Agile teams. Teams that use Kanban first understand how they currently build software, and then improve that process gradually.

Simple Meaning

Kanban = Visualize the Work + Limit the Work in Progress + Improve the Flow Continuously
  • Kanban does not necessarily tell a team to completely replace its existing process.
  • Instead: Start with the existing process → visualize it → identify problems → improve it continuously.
Running Example — Introducing CAMS

A software team is developing a College Attendance Management System (CAMS) — allowing faculty to mark attendance, students to view their attendance percentage, and administrators to generate reports. Their existing process is:

Requirement → Analysis → Development → Testing → Release

Instead of immediately introducing a completely new methodology, the team places these stages on a Kanban board:

BACKLOG → ANALYSIS → DEVELOPMENT → TESTING → RELEASE

Now everyone can see:

  • What work has not started?
  • What is currently being developed?
  • What is waiting for testing?
  • Where is work getting stuck?

That visibility allows the CAMS team to improve its process.

Important Distinction (Exam Point)

Kanban is not simply a board.

  • The board is a tool for visualizing the workflow.
  • Kanban is a method for improving the flow of work.

02 History & Origin

  • Kanban is a manufacturing term, adapted for software development and associated with David Anderson.
  • It is connected conceptually to the Toyota Production System, Lean Manufacturing, and Just-in-Time (JIT) production.

03 Kanban in Manufacturing and Software

Manufacturing Example

In a car manufacturing plant, a car passes through: Raw Material → Body Construction → Painting → Assembly → Quality Inspection → Delivery. If the painting section can process only 10 cars but assembly sends 20 cars, cars accumulate between the stages. That accumulation is a bottleneck. Kanban helps control how much work enters each stage.

Software Equivalent — CAMS

Workflow: Requirements → Development → Testing → Deployment. Suppose CAMS developers complete 20 features (e.g., attendance marking, percentage calculation, alerts) but testers can test only 5. Then Development = 20 items, Testing = 5 items — the remaining 15 items become work in progress waiting for testing. Kanban attempts to prevent such excessive accumulation.

Fig. 3.1 — Development output exceeding Testing capacity produces WIP accumulation

04 Kanban Mindset

  • Kanban, like Scrum, requires a mindset.
  • It is not just "draw some columns and put sticky notes."
  • The team adopts a way of thinking based on: continuous improvement, visibility, collaboration, respect, customer focus, flow, and limiting WIP.
Illustration

Suppose the CAMS Testing column contains 15 tasks.

  • Wrong mindset: "Let's add five more development tasks."
  • Kanban mindset: "Why are so many tasks waiting for testing?" — possible causes: insufficient testers, unclear requirements, too many defects, testing environment unavailable, developers producing work faster than testing capacity.
Key Point (Exam Point)

The objective is to fix the system, rather than simply push more work into it.

SEE THE WORK → UNDERSTAND THE WORK → CONTROL THE WORK → IMPROVE THE FLOW
Foundations

05 Kanban Values

The PPT introduces nine Kanban values: Transparency, Balance, Collaboration, Customer Focus, Workflow (Flow), Leadership, Understanding, Agreement, and Respect.

Fig. 5.1 — The nine Kanban values

5.1 Transparency

Meaning

An open exchange of information and clear, unambiguous terminology. Everyone should understand what work exists, where it is, and what is blocking it.

Illustration

A CAMS card shows: "Login Module → Development." But the developer is actually waiting for database credentials. A transparent board makes that visible: "Login Module — Status: Development — Blocked: Waiting for DB credentials." Now the team can act.

Exam Point

Transparency = making workflow status and problems visible to everyone.

5.2 Balance

Balancing the different requirements, views, and abilities of participants against each other.

Illustration

CAMS developers complete 10 features/day; testers can handle only 3 features/day. This is unbalanced — development continuously outpaces testing, and the testing queue grows. Kanban encourages the team to identify and correct this imbalance.

5.3 Collaboration

The Kanban method improves how people work together — a key value because Kanban encourages team-level responsibility for flow, rather than isolated departmental responsibility.

Illustration

A CAMS attendance-percentage feature is stuck in testing. Instead of "that's the testing team's problem," the developer asks "Can I help reproduce the issue?" and the tester responds "Yes — it occurs with invalid roll numbers." Both work together to move the item forward.

5.4 Customer Focus

The customer is the natural centre of interest in Kanban.

Illustration

A department needs low-attendance SMS alerts. The CAMS team should prioritize work that delivers meaningful student/faculty value, instead of spending excessive time on low-value internal features while this customer-critical functionality waits. The guiding question: "Why are we developing this feature?" — the answer should connect to customer/user value.

5.5 Workflow (Flow)

Work represents a continuous or occasional flow of value; recognizing and maintaining that flow is one of the most important Kanban concepts.

Analogy — Water Through Pipes

Source → Pipe → Pipe → Pipe → Destination. If one pipe is blocked, water accumulates before the blockage. Software work behaves similarly: if CAMS Testing becomes a bottleneck, work accumulates before it. Kanban tries to achieve smooth flow.

5.6 Leadership

Leadership is required at all levels to generate value and achieve an improved state — not restricted to a Project Manager, Team Leader, or Manager. A CAMS developer can identify a process problem; a tester can suggest improvement; any team member can propose a better workflow.

5.7 Understanding

Understanding connects to self-awareness at both individual and organizational levels; before improving a process, the team must understand how it works, why it works that way, where problems occur, what constraints exist, and how people interact with the process.

Illustration

If CAMS testing always takes 3 days, the team should not immediately conclude "testers are slow" — instead investigate: are requirements unclear? Are test cases difficult to prepare? Is the test environment unstable? Are developers producing too many defects?

Understanding comes before improvement.

5.8 Agreement

All parties agree to pursue goals together, while respecting different opinions and approaches.

Illustration

The CAMS team wants to set Development WIP Limit = 4. Developers, testers, and managers should understand and agree on why the limit exists — not "the manager told us WIP = 4," but "we agree that 4 allows us to maintain manageable work and improve flow."

5.9 Respect

Definition (Exam Point)

Respect for people — through appreciation, understanding, and consideration — is the foundation for the other Kanban values.

Illustration

If a CAMS task is delayed, Kanban does not mean blaming "the developer is inefficient." Instead ask: "What is preventing this work item from flowing?" Kanban focuses on improving the system, not blaming individuals.

Foundations

06 Kanban Principles

Kanban rests on four principles.

Fig. 6.1 — The four Kanban principles
1. Start With What You Do Now

Kanban begins from the CAMS team's existing process rather than demanding a rebuild. "Let's understand this process first," not "this process is wrong."

2. Incremental, Evolutionary Change

Change happens gradually: Problem → Understand → Small Experiment → Measure → Learn → Improve — not a wholesale process replacement.

3. Respect Current Roles & Titles

Existing roles (Product Owner, Developer, Tester, Project Manager) are respected; adopting Kanban does not require immediate restructuring.

4. Encourage Leadership at All Levels

Any CAMS team member — developer, tester, analyst, or manager — can initiate improvement.

Board & Workflow

08 Workflow Visualization

Key Phrase (Exam Point)

Visualize the actual workflow — not the ideal workflow.

  • The first step in improving a process is understanding how the team currently works.
  • Visualization means recording what the team actually does, without embellishing it.
Illustration — Official vs. Actual CAMS Workflow

Official process: Analysis → Development → Testing → Release.

Actual process: Analysis → Development → Code Review → Rework → Development → Testing → Bug Fixing → Testing → Release.

The Kanban board should reflect the actual process — because visualizing an imaginary process makes it impossible to identify real bottlenecks.

8.1 Why Visualization Is Powerful

Illustration

Consider 20 CAMS work items distributed as: Backlog 5, Development 3, Testing 10, Release 2. Immediately, the board reveals that Testing is accumulating work. Without visualization, management might simply say "the project is progressing." The Kanban board instead says: "Work is progressing, but Testing is becoming a bottleneck" — far more useful for process improvement.

09 Kanban Board

Definition

A Kanban board is a tool for visualizing workflow, typically using columns and cards/sticky notes.

Fig. 9.1 — A basic Kanban board for CAMS. Each card is a work item moving Backlog → Development → Testing → Done.

9.1 Kanban Card

Definition (Exam Point)

A Kanban card is a visual representation of a work item.

For example, a card labelled [Implement Attendance Marking] moves: Backlog → Development → Testing → Done.

9.2 Kanban Board vs. Scrum Task Board — Three Key Differences

Kanban Board vs. Scrum Task Board (Exam Point)

A documented real-world Kanban workflow used these columns: Input Queue → Analysis (In Progress) → Analysis (Done) → Development Ready → Development (In Progress) → Development (Done) → Build Ready → Test → Release Ready. This demonstrates that Kanban can model a detailed real-world workflow, and lets the team identify exactly where an item is waiting.

10 WIP & WIP Limits

Definition (Exam Point)

WIP = Work In Progress — work currently inside the workflow. Limiting WIP means setting a limit on the number of work items that can be in a particular workflow stage.

Illustration

Suppose CAMS Development WIP Limit = 3, and Development currently holds [Login], [Attendance Marking], [Reports] — already three items. A new feature cannot simply be pushed into Development. Instead, the team asks: "Can we finish one of the existing items?" This encourages finishing work instead of starting more work.

10.1 Why Too Much WIP Is Dangerous

  • Accepting more work than the team can accomplish can result in: unfinished work, poor-quality development, and an unsustainable working pace.
Illustration — The Illusion of Productivity

Five CAMS developers start eight features simultaneously (A through H). Everyone is busy — but nothing gets completed. This is the illusion of productivity.

Better approach: WIP LIMIT = 3. Only three features are actively worked on. Once Feature A finishes, the team pulls Feature D into development. This supports smoother flow.

Reference Example — Manager Review Column

The source PPT specifically shows a WIP limit of 10 in the "Manager Review" column. If 8 items are present, a new item can enter; but once 10 items are present, the column is full, and the upstream team should not continue pushing additional work into it — instead, the review bottleneck itself must be resolved.

Fig. 10.1 — A full WIP-limited column blocks new work from entering
Board & Workflow

11 Push vs. Pull System

WIP limits naturally support a pull-based system.

Fig. 11.1 — Push versus Pull systems
Illustration — CAMS

Workflow: Analysis → Development → Testing. Development WIP limit = 3, currently holding R1 | R2 | R3. New work R4 arrives — it cannot enter because current WIP (3) equals the WIP limit (3). When R1 moves to Testing, Development becomes R2 | R3 | empty, and R4 can now be pulled in: R2 | R3 | R4.

Flow & Measurement

12 Flow & Bottlenecks

Definition (Exam Point)

Flow is the rate at which work items move through the system. The team measures workflow and adjusts WIP limits to improve flow.

"How smoothly and quickly is work moving from start to finish?" — NOT "How many tasks have developers started?"

The focus is the movement of completed value, not the count of started activity (recall Activity ≠ Flow, §1).

12.1 Bottleneck

Definition

A stage whose capacity is lower than the stages feeding it, causing work to accumulate before it.

Illustration — CAMS Capacity Table

Workflow: Analysis → Development → Testing → Release.

CAMS Stage Capacities
StageCapacity
Analysis8/day
Development7/day
Testing3/day
Release5/day

Testing has the lowest capacity; therefore, Testing is likely to become the bottleneck, and work accumulates before it.

13 Throughput & Lead Time

Throughput
The number of work items completed per unit of time.
Lead Time
The average time a work item takes to move from entry to completion.

13.1 Numerical Example — Throughput

Illustration — CAMS Weekly Completions
DayItems Completed
Monday2
Tuesday3
Wednesday2
Thursday3
Friday2
Total12

Formula: Average Throughput = Total Completed ÷ Days
Substitute: 12 ÷ 5
Answer: 2.4 items/day

This gives the CAMS team an understanding of its delivery flow. Throughput and Lead Time are connected quantitatively by Little's Law (§17).

Flow & Measurement

14 Cumulative Flow Diagram (CFD)

Definition (Exam Point)

The Cumulative Flow Diagram (CFD) is an effective tool for measuring flow. It tracks how work accumulates across workflow stages over time.

Analogy — Water Tank

If water enters a tank faster than it leaves, the water level rises. Similarly, if work enters a stage faster than it leaves, WIP rises. The CFD visualizes this accumulation over time.

Fig. 14.1 — Conceptual CFD for CAMS: cumulative work items across Development, Testing, and Done bands over time

14.1 Why Use a CFD?

It helps identify:

  • WIP accumulation
  • Bottlenecks
  • Changes in flow
  • Stability of the workflow
Interpretation (Exam Point)

If the Testing band in Fig. 14.1 keeps widening over time, this indicates increasing accumulation in Testing — the CAMS bottleneck identified in §12 becomes visible directly on the diagram.

15 Explicit Process Policies

  • Kanban teams do not need huge documents or wikis to establish policies.
  • Policies can be as simple as WIP limits or definitions of done/exit criteria.
What Does "Explicit" Mean? (Exam Point)

Everyone should know: "What conditions must be satisfied before work moves to the next stage?"

15.1 Why Collaborative Policies Matter

Policies are particularly effective when established collaboratively and evolved experimentally by the whole team — this means policies are not necessarily permanent.

Illustration

Suppose CAMS Testing WIP = 5. After observing the system, the team discovers that 5 creates excessive context switching. They experiment with Testing WIP = 3, then measure whether flow improves.

Observe → Experiment → Measure → Improve
Flow & Measurement

16 Definition of Done

Illustration

Suppose CAMS has: Testing → Done. What does "Done" mean? The team defines:

  • ✓ All test cases executed
  • ✓ No critical defects
  • ✓ Required documentation completed
  • ✓ Customer (department) acceptance obtained

Now everyone understands the same rule.

Without Explicit Policies (Exam Point)

Without an agreed Definition of Done, a developer may say "I think it's done," while a tester says "No, it's not ready" — creating confusion and rework.

Flow & Measurement

17 Little's Law

This is the quantitative section of the Kanban unit.

Formula (Exam Point)

L = W × λ

W = L ÷ λ

SymbolMeaning
λArrival rate
LInventory / average WIP
WAverage lead time
Fig. 17.1 — Little's Law: Inventory (L), Lead Time (W), and Arrival Rate (λ)

17.1 Numerical Example 1 — Hospital Analogy

Illustration

Patients arrive at 10 patients/hour, and the average number of patients in the system is 5 patients.

Formula: W = L ÷ λ
Substitute: W = 5 ÷ 10
Answer: W = 0.5 hour (30 minutes)

17.2 Numerical Example 2 — PPT's Office Patient Example

Illustration

An office schedules 11 patients to arrive every hour (λ = 11/hour), with an average inventory of 7 patients (L = 7) over the course of the day.

Formula: W = L ÷ λ
Substitute: W = 7 ÷ 11 = 0.63 hours
Answer: W ≈ 37–38 minutes

17.3 Numerical Example 3 — Little's Law in CAMS

Illustration

The CAMS team has average WIP = 20 items and throughput = 5 items/week.

Formula: W = L ÷ λ
Substitute: W = 20 ÷ 5
Answer: W = 4 weeks

Now suppose the CAMS team reduces WIP to 10 items, with throughput remaining 5 items/week:

W = 10 ÷ 5 = W = 2 weeks

Powerful Insight (Exam Point)

Reducing WIP can reduce lead time when throughput remains stable. Conceptually: More WIP → Longer Lead Time → More Waiting, provided arrival/throughput conditions are stable — one reason Kanban emphasizes limiting WIP.

18 Continuous Improvement

The PPT's central story, connecting every practice into one continuing cycle:

Fig. 18.1 — Complete Kanban flow: from visualization to continuous improvement
"See the work → Limit the work → Measure the flow → Improve the process."

18.1 Feedback Loops & Collaborative, Experimental Evolution

  • Feedback Loops: Action → Observe → Feedback → Change → New Action, repeating continuously.
  • Improve Collaboratively, Evolve Experimentally: changes are proposed by the whole team and tested as hypotheses, not assumed to work: Observe → Experiment → Measure → Improve (§15.1).

19 Complete Case Study — College Attendance Management System

Students are developing the College Attendance Management System (CAMS), applying every Kanban concept covered above in sequence.

Backlog → Analysis → Development → Testing → Deployment → Done

19.1 Step 1 — Visualize

CAMS Kanban Board Snapshot
BacklogAnalysisDevelopmentTestingDone
LoginAttendance ModulePercentage Calc.—Profile
Fee Payment—Notification——
Reports————

Immediately, the team can see the current state of every item.

19.2 Step 2 — Add WIP Limits

Analysis WIP = 2  |  Development WIP = 3  |  Testing WIP = 2

Now the team cannot endlessly start new work.

19.3 Step 3 — Detect Bottleneck

Illustration

Development → 3 items (full); Testing → 2 items (full). Developers should not simply start another feature — instead, they help move existing items toward completion.

19.4 Step 4 — Measure Flow (Little's Law)

Illustration

The CAMS team completes 10 items/week, with average WIP of 20 items.

Formula: W = L ÷ λ
Substitute: W = 20 ÷ 10
Answer: Average lead time ≈ 2 weeks

19.5 Step 5 — Improve (Experiment)

Illustration

The team experiments: WIP: 20 → 15. If throughput remains approximately 10 items/week:

W = 15 ÷ 10 = 1.5 weeks

The team then evaluates whether the change actually improves delivery — this is data-driven continuous improvement.

20.3 Two-Mark Questions with Answers

2 MARKSDefine Kanban.
Kanban is a method for process improvement used by Agile teams; it visualizes the workflow, limits work in progress, and improves flow continuously, starting from the team's existing process.
2 MARKSWhat is a Kanban board?
A tool used to visualize the workflow, typically consisting of columns representing workflow stages and cards representing work items.
2 MARKSWhat is WIP?
Work In Progress — work items that have entered the workflow but have not yet been completed.
2 MARKSWhat is a WIP limit?
A restriction on the number of work items permitted in a given workflow stage at one time, used to prevent overload and encourage finishing work.
2 MARKSDefine workflow.
The sequence of stages through which a work item passes from request to completion, e.g., Analysis → Development → Testing → Release.
2 MARKSWhat is a bottleneck?
A workflow stage whose capacity is lower than the stages feeding it, causing work to accumulate before it and slowing overall delivery.
2 MARKSWhat is a Cumulative Flow Diagram?
A tool that tracks how work accumulates across workflow stages over time, used to identify WIP, bottlenecks, and flow stability.
2 MARKSState Little's Law.
L = W × λ (equivalently W = L ÷ λ), where L is average inventory/WIP, W is average lead time, and λ is arrival rate — valid for a stable workflow.
2 MARKSWhat is meant by explicit process policies?
Clearly stated, visible rules — such as WIP limits, exit criteria, and definitions of done — describing the conditions under which work may move to the next stage.
2 MARKSMention any four Kanban values.
Any four of: Transparency, Balance, Collaboration, Customer Focus, Workflow, Leadership, Understanding, Agreement, Respect.

20.5 One-Line Memory Trick

Core Conceptual Thread

“See the work → Limit the work → Measure the flow → Improve the process.”

Or: VISUALIZE → LIMIT WIP → MEASURE FLOW → MAKE POLICIES EXPLICIT → CONTINUOUS IMPROVEMENT.

Closing Statement

Kanban is a mindset for seeing work, limiting work in progress, and improving flow continuously — starting from the current process, changing incrementally, respecting existing roles, and encouraging leadership at every level. Its board, WIP limits, CFD, and Little's Law exist to make this improvement cycle visible and measurable, as demonstrated throughout by the College Attendance Management System.
